ROOT CAUSE ANALYSIS
================================================================================

PROBLEM 1: Highlights misalign and disappear in paginated mode
--------------------------------------------------------------------------------
Root cause: coordinate space mismatch — two independent spaces are being
confused as one.

In _ReaderPageState._onDocumentLoaded (reader_page.dart:109):

  final size = details.document.pages[0].size;
  setState(() {
    _pageSize = Size(size.width, size.height);

details.document.pages[0].size returns the PDF LOGICAL page size — PDF
user-space units (typically 1 point = 1/72 inch), e.g. 612x792 for A4.
This is a document-space measurement with no relationship to screen pixels.

SfPdfViewer then applies its own internal render transform to fill the viewport:

  PDF user-space (612x792) -> render pixels (390x504 on a 390px-wide phone)

The scale factor is approximately:
  scale = (screenWidth - margins) / pdfWidth

SfPdfViewer never exposes this scale factor.

In GestureHandler._onDragEnd (gesture_handler.dart:60-67):

  final rect = Rect.fromPoints(start, end);
  ref.read(annotationNotifierProvider.notifier).addHighlight(
    rect: toRelative(rect, widget.pageSize),
    ...
  );

start and end are localPosition from DragStartDetails/DragUpdateDetails —
these are Flutter SCREEN PIXELS, relative to the GestureHandler widget's
top-left. widget.pageSize is the PDF logical size (612x792).

So toRelative divides screen pixels by PDF points (coordinate_mapper.dart:24-31):

  RelativeRectModel(
    left: absoluteRect.left / pageSize.width,   // screenPx / pdfPoints — WRONG
    top:  absoluteRect.top  / pageSize.height,  // screenPx / pdfPoints — WRONG
    ...
  )

The relative values produced are wrong by a factor of approximately 1.6x on a
typical phone (612 PDF pts vs ~390 screen px).

Then HighlightPainter renders (highlight_painter.dart:41-47):

  final absoluteRect = toAbsolute(rect, pageSize);
  canvas.drawRect(absoluteRect, paint);

The canvas size in paint(Canvas, Size) is the actual SCREEN size of the
CustomPaint widget (SizedBox.expand() — full viewport). But pageSize (passed in)
is again the PDF logical size.

RESULT: Both the write path (gesture -> relative) and the read path
(relative -> paint) have the same wrong scale applied, so they partially cancel
out — highlights appear approximately correct when the PDF exactly fills the
viewport with no zoom. But:

  - Any zoom level change breaks alignment
  - Paginated vs continuous mode renders the page at different viewport fills
  - Different screen sizes and DPRs produce different fills
  - Page margins/spacing (pageSpacing: 4) are not accounted for
  - Pages after page 0 with different sizes are completely wrong (see 1b below)

PROBLEM 1b: First-page size used for all pages

  // reader_page.dart:109 — only ever reads page[0]
  final size = details.document.pages[0].size;

If the PDF has mixed page sizes (landscape page in a portrait document),
every page after the first has wrong coordinate scaling.

WHY IT DISAPPEARS IN PAGINATED MODE SPECIFICALLY:
In PdfPageLayoutMode.single, SfPdfViewer fits one page to fill the viewport
width. In PdfPageLayoutMode.continuous, pages render more consistently relative
to the container. The render geometry differs between modes, so annotations that
appear roughly correct in one mode are visibly wrong in the other.


PROBLEM 2: Text selection is unreliable
--------------------------------------------------------------------------------
The app does not use SfPdfViewer's text selection for annotation creation.
The annotation system uses a custom rectangle drag — not text-aware at all.

PdfInteractionMode.selection is only active during normal reading:

  // reader_page.dart:480-482
  final interactionMode = _annotating
      ? PdfInteractionMode.pan
      : PdfInteractionMode.selection;

When _annotating = true, the viewer switches to pan mode, disabling the
viewer's own selection, and GestureHandler takes over with raw drag detection.
There is no bridge from SfPdfViewer's selection events to the annotation system.

Consequence: when not in annotation mode, SfPdfViewer selection works, but its
results (selected text, selection rects) are never captured for annotation.
When in annotation mode, selection is disabled and replaced by a freehand
rectangle drag that has the coordinate problem above.

ADDITIONALLY: _ScrollAmplifier wraps the viewer with a Listener that reads
pointer events even outside annotation mode:

  // reader_page.dart:901-917
  void _onPointerMove(PointerMoveEvent e) {
    final extra = -dy * _ScrollAmplifier.amplification;
    widget.controller.jumpTo(xOffset: current.dx, yOffset: current.dy + extra);
  }

The jumpTo calls fight SfPdfViewer's own scroll physics. This can interfere
with gesture recognition and cause the viewer to intermittently ignore input.


PROBLEM 3: Highlights are position-bound rather than text-bound
--------------------------------------------------------------------------------
The model stores four normalized floats and nothing else:

  // relative_rect_model.dart
  class RelativeRectModel {
    final double top, left, bottom, right;
  }

Annotation.text is only populated for notes. There is no selectedText,
no character index, no text range. Highlights have zero text context stored.

WHAT SYNCFUSION EXPOSES FOR TEXT ANCHORING:

syncfusion_flutter_pdf (the non-viewer package) has:
  - PdfPage.extractText() — extracts all text from a page as a flat string
  - PdfTextExtractor class with word and line boundary detection
  - PdfTextLine, PdfTextWord, PdfTextElement with bounding rectangles
  - No character-index API that maps to screen positions

SfPdfViewer (the viewer package) exposes via selection:
  - PdfViewerController.getSelectedText() — returns the selected text string
  - Selection rect callback (not wired in this codebase, but available via
    onTextSelectionChanged)

Text extraction bounding boxes from syncfusion_flutter_pdf are in PDF coordinate
space (same units as pages[0].size), not screen pixels.

================================================================================
ANNOTATION ANCHORING STRATEGY: EVALUATION
================================================================================

OPTION A: Coordinate-based (current approach)
Stores visual coordinates normalized to page size.

  PRO: Simple to implement, no dependency on text extraction
  PRO: Works for non-text annotations (drawn shapes, image areas)
  CON: Fails when render scale changes if coordinates were captured at a
       different scale
  CON: Requires knowing the exact render transform at both capture and display
  CON: Cannot locate "what text is highlighted" — can't integrate with search,
       copy, or accessibility

VERDICT: Viable only if the coordinate space is correctly defined as PDF
user-space (not screen pixels). Currently broken because both capture and
display use screen pixels disguised as PDF points.


OPTION B: Text-range anchoring
Store the character start/end index within the page's extracted text string,
plus the verbatim selected text.

  PRO: Survives zoom changes, orientation changes, DPI differences
  PRO: Can be restored by re-extracting text and finding the text range
  PRO: Enables copy, share, search integration
  CON: Requires PdfTextExtractor to extract text on annotation creation and
       on render (~50-200ms per page)
  CON: Fails if PDF is regenerated with different text layout
  CON: Character indices are fragile if text contains markup or encoding issues
  CON: Requires matching bounding boxes from extraction to screen coordinates —
       the same transform problem, just deferred to extraction time


OPTION C: Hybrid anchoring (RECOMMENDED)
Store both a text anchor and a visual fallback:

  selectedText:   "the actual selected text"
  textRunStart:   character index in page text
  textRunEnd:     character index in page text
  relativeBounds: normalized PDF-unit rect (0.0-1.0 of PDF page dimensions)

HOW IT WORKS:

At capture time:
  After the user creates an annotation, run PdfTextExtractor on the affected
  page. Find which text lines/words fall within the drag rect (in PDF
  coordinates after correcting the coordinate bug). Store the verbatim text
  content and the PDF-unit bounding rect normalized to 0-1.

At render time:
  Use the normalized PDF-unit bounding rect to compute screen coordinates:

    screenX = rel.left * renderedPageWidthInPixels
    screenY = rel.top  * renderedPageHeightInPixels

  renderedPageWidthInPixels must be measured, not assumed — see coordinate
  fix below.

If text anchor is available:
  Verify the stored text exists at the expected location. If it has moved,
  use a fuzzy text match to relocate the annotation.

VERDICT: Option C is the production-grade choice. It degrades gracefully —
if text extraction fails, the visual bounds still work. If zoom changes, the
text anchor provides ground truth.

COORDINATE SYSTEM FIX (THE CRITICAL FIX)
================================================================================

The correct pageSize to use in toRelative and toAbsolute is the RENDERED SCREEN
SIZE of the PDF page, not the PDF logical size.

With SfPdfViewer you can infer the rendered page size using LayoutBuilder:

  // In _ReaderPageState, add:
  Size _renderedPageSize = Size.zero;

  // In _buildViewer(), wrap SfPdfViewer in LayoutBuilder:
  LayoutBuilder(
    builder: (context, constraints) {
      final availableWidth = constraints.maxWidth;
      if (_pageSize != Size.zero) {
        final aspectRatio = _pageSize.height / _pageSize.width;
        final renderedHeight = availableWidth * aspectRatio;
        if (_renderedPageSize.width != availableWidth) {
          WidgetsBinding.instance.addPostFrameCallback((_) {
            if (mounted) {
              setState(() {
                _renderedPageSize = Size(availableWidth, renderedHeight);
              });
            }
          });
        }
      }
      return SfPdfViewer.file(...);
    },
  )

Then pass _renderedPageSize to GestureHandler and HighlightPainter instead of
_pageSize. _pageSize (PDF logical size) is only needed for aspect ratio
calculation and for PdfTextExtractor coordinate math.

IMPORTANT CAVEATS:
  - SfPdfViewer applies its own internal margins. The actual PDF page within
    the viewport may not start at (0, 0). Measure or hard-code the margin to
    subtract from gesture coordinates.
  - At zoom level > 1.0, the rendered page is larger than the viewport. You
    need to account for scroll offset when mapping gesture coordinates.
  - In continuous mode with page spacing (pageSpacing: 4), the vertical offset
    of each page changes. Each page's top-left in screen space equals the sum
    of all preceding rendered page heights plus spacing. This makes per-page
    annotation in continuous mode significantly more complex.

================================================================================
TEXT ANCHORING IMPLEMENTATION PLAN
================================================================================

For highlights, the flow after the coordinate bug is fixed:

1. User drags -> GestureHandler captures drag rect in screen pixels
2. Convert screen rect -> PDF user-space rect using rendered page size
3. Use syncfusion_flutter_pdf.PdfTextExtractor to find all PdfTextLine /
   PdfTextWord objects whose bounding rects intersect the PDF user-space rect
4. Collect those words -> selectedText = words.map((w) => w.text).join(' ')
5. Collect the union bounding rect of all matching words -> store as
   RelativeRectModel normalized to PDF page size (0.0-1.0)
6. Store textRunStart and textRunEnd as character positions in the full page
   text string

At render time, the RelativeRectModel (in PDF user-space) maps to screen pixels:

  screenRect = Rect.fromLTRB(
    rel.left  * renderedWidth,
    rel.top   * renderedHeight,
    rel.right * renderedWidth,
    rel.bottom * renderedHeight,
  )

This is only accurate if renderedWidth is the true rendered page width in screen
pixels — which requires the LayoutBuilder measurement described above.

MIGRATION STRATEGY
================================================================================

Coordinate data stored under DB versions 1-3 is in the incorrect coordinate
space (screen pixels normalized by PDF logical size). This data cannot be
recovered to true PDF user-space coordinates without knowing the screen size
and DPI at capture time — which were not stored.

RECOMMENDED APPROACH:

- In migration v4: add new columns (selected_text, text_run_start, text_run_end,
  pdf_width, pdf_height, coordinate_version)
- Do NOT attempt to backfill old coordinate data — it cannot be corrected
- Mark all existing annotations pre-v4 with coordinate_version = 1
- At render time, render coordinate_version = 1 annotations with a visual
  indicator: "This annotation may be misaligned — it was created before an
  app update" — or render as-is and let users delete/re-create
- New annotations store coordinate_version = 2 with corrected coordinates

This is the honest, user-respecting approach. Silently "correcting" old
coordinates with a heuristic will produce worse results than acknowledging
the issue.
